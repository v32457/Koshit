AUTHORITATIVE BUSINESS DECISIONS – OVERRIDE ANY OLDER CHECKLIST WORDING

The decisions below are confirmed by the business owner and are
requirements, not suggestions. If any earlier section or old checklist
wording conflicts with these decisions, this section takes precedence.
Do not treat a REQUIRED feature as optional. Do not implement a NOT
REQUIRED feature.

1.  Scope remains Phase 1 Purchase Request (PR) only. Do not implement
    PO creation/modification, Direct PO, PR-to-PO conversion, PR
    consolidation into PO, partial PR-to-PO allocation, PO quantity
    allocation, PO approval, or PO tracking screens. Read-only display
    of existing open PO/commitment information is allowed only where the
    authorized ERP integration exposes it; it must not create or modify
    POs.
2.  Reuse the existing CIPPlatform architecture, masters, RBAC, approval
    engine, ERP integration, budget controls, Communication and
    Notification Hub, audit services, and database conventions. Do not
    create duplicate masters, parallel workflow engines, or a standalone
    application.
3.  PR applicability must be evaluated before displaying the PR menu and
    enforced again on every backend operation. Missing, invalid, or
    ambiguous configuration denies access by default.
4.  PR Types are MRP, Manual, Repair, and Maintenance, configurable
    through existing General Settings. PR Type is distinct from Item
    Category. Equipment/machine ID remains optional for Repair and
    Maintenance.
5.  Support material and service PR lines. Non-catalogue items/services
    must pass controlled master-data review; no uncontrolled master
    creation or duplicate master records.
6.  MRP must support manual import and automatic authorized ERP
    integration, with reviewable drafts, source traceability, duplicate
    prevention/idempotency, batch history, retry, reconciliation, and
    exception reporting. Never fabricate MRP data.
7.  Buyer assignment is resolved from existing Item Master/branch
    mapping. Do not guess or silently auto-assign a missing buyer; flag
    Pending Buyer Configuration and notify the authorized administrator.
8.  Duplicate PR detection is a warning, not an automatic rejection or
    merge. Record acknowledgement/justification as configured.
9.  Budget controls are configured by branch and item category with
    enable/disable settings. When enabled for the applicable
    branch/category, mandatory configured budget checks apply before
    submission; insufficient budget, missing required assignment, or
    unavailable authoritative budget validation blocks submission unless
    an authorized budget-exception workflow is approved. When explicitly
    disabled by authorized configuration, do not run that budget gate
    for the applicable scope. Project/WBS budget check is NOT REQUIRED.
    Do not infer a budget source or fabricate budget data.
10. UOM rule: every PR material line uses the Item Master Inventory UOM
    as its authoritative and displayed PR UOM. The requester cannot edit
    or replace it. If an alternate purchasing/display conversion is
    required by an approved business process, use configured approved
    conversion factors only, show the conversion transparently, and
    retain the Inventory-UOM quantity as the authoritative quantity. No
    free-text or user-defined conversion.
11. Stock/inventory values must come from the existing authorized ERP
    integration. Show warehouse-level and multi-warehouse availability,
    stock ageing, batch/lot and serial details only where applicable to
    the item, open PR quantity, and open PO/commitment visibility only
    if ERP exposes it. Stock-transfer suggestions must be based on
    actual available stock and ageing data. Show retrieval timestamp and
    freshness; stale/unavailable data must be clearly flagged and must
    never be treated as zero or current. No inventory
    reservation/deduction unless an existing authorized ERP process does
    it.
12. Approved alternate/substitute suggestions may be shown only when the
    alternate is already configured as approved and stock is actually
    available. Do not recommend unapproved or unavailable alternates.
13. Approval must use the existing Approval Workflow Engine. Reporting
    Manager Level 1 remains mandatory unless an explicitly authorized
    exception is already supported and configured. Support parallel and
    sequential approvals, item-level approvers, partial quantity
    approval/rejection, delegation with start/end dates, SLA
    escalation/reminders, withdrawal before final approval, and
    approval-rule version retention. No ambiguous or missing rule may
    bypass approval.
14. Partial approvals must preserve requested, approved, rejected,
    returned, and pending quantities at line level. Approved quantity
    cannot exceed requested quantity. Parent PR status is derived from
    line and workflow states.
15. PR edits are frozen during active approval. Approved changes by
    requester, assigned buyer, or authorized administrator require a
    change request, reason, before/after comparison, budget revalidation
    where applicable, configured reapproval, and preservation of the
    previous approved version.
16. Stale unapproved line cleanup is REQUIRED. XX days is an
    administrator-configured value, not a hardcoded default. Cleanup
    must support preview, authorized manual or scheduled execution,
    advance warning, exemptions, soft archive only, full audit,
    skipped/error reporting, parent-status recalculation, and authorized
    restoration. Approved lines and approved quantities must never be
    removed. Eligible unapproved balances on partially approved lines
    may be archived only if explicitly configured. Do not physically
    delete PR headers or lines.
17. PR closure may be manual or automatic only under explicit General
    Settings rules. Approval alone does not close a PR. PO conversion or
    receipt completion cannot be a Phase 1 closure condition.
18. Priority values are Normal, Urgent, and Critical, with role-based
    controls, justification where configured, audit, and no approval
    bypass.
19. The 100-feature decision register below is authoritative: 99
    features are REQUIRED and feature 33 (budget check by project/WBS)
    is NOT REQUIRED. Feature 46 (dated approval delegation) is REQUIRED.
20. No implementation may claim that an integration or feature works
    until the existing source code, configuration, interface and runtime
    behaviour have been inspected and the relevant tests have passed.
    Where ERP/master-data capability is not present, document the gap
    and required interface contract; do not mock or fabricate production
    data.

CIPPlatform – Purchase Request (PR) Module

Phase 1 – Consolidated Functional and Technical Implementation
Specification

1.  Objective and Scope

Implement the Purchase Request module within the existing CIPPlatform
application.

Phase 1 is strictly limited to PR functionality.

Reuse existing: - Authentication and RBAC. - Employee and Reporting
Manager hierarchy. - Company, Branch, Group and Department masters. -
Business Unit / Plant masters. - Unit-specific Item Master. - Item
Category and UOM masters. - General Settings. - Existing Approval
Workflow Engine. - Existing ERP integration. - Budget and cost-centre
functionality, where available. - Audit and notification services.

Do not create duplicate masters, standalone applications or separate
approval engines.

Explicitly excluded from Phase 1

Do not implement: - PO creation or modification. - Direct PO
functionality. - PR-to-PO conversion. - Multiple PR consolidation into
one PO. - Partial PR-to-PO allocation. - PO quantity allocation
controls. - PO approval workflow. - PO tracking screens.

Keep the PR data model compatible with future PO integration without
implementing PO functionality now.

Before coding, inspect:

1.  Frontend framework and navigation.
2.  Authentication and RBAC.
3.  Employee master and reporting hierarchy.
4.  Company, branch, group and department masters.
5.  Business unit / plant masters.
6.  Unit-specific Item Master.
7.  Item category and UOM masters.
8.  Branch-specific buyer assignment.
9.  General Settings.

Configuration changes. - ERP integration dependencies. - Regression

Do not modify source files until the assessment and implementation plan
have been presented.

3.  PR Type Classification

PR Type is mandatory.

Initial PR types:

  PR Type       Description
  ------------- -----------------------------------------
  MRP           Material Requirements Planning
  Manual        Manually initiated purchase requirement
  Repair        Repair-related requirement
  Maintenance   Maintenance-related requirement

PR Type must be configurable through existing General Settings.

Administrators can enable, disable or add PR types without code changes.

PR Type and Item Category must remain separate fields.

A Maintenance PR, for example, may contain electrical spares, mechanical
spares or consumables.

4.  PR Type-Specific Functionality

4.1 MRP PR

Support both generation methods:

Option A – Manual import - Import MRP-generated requirements from an
approved ERP export or supported import interface. - Validate the
imported data. - Map item codes to the correct CIPPlatform Item
Master. - Validate quantities and delivery dates. - Capture the source
MRP reference. - Show imported records for user review before PR
submission.

Option B – Automatic ERP integration - Retrieve MRP requirements through
an authorized existing ERP integration. - Identify the source planning
run. - Retrieve required items and quantities. - Retrieve required
delivery dates. - Validate branch and business-unit ownership. -
Generate PR draft records for review and submission. - Record source
transaction identifiers to prevent duplicate imports.

Both methods must be supported.

Do not fabricate MRP data or simulate ERP availability.

If the existing ERP integration does not expose the required MRP data,
document the interface gap and request the necessary integration details
before implementation.

Capture, where available: - MRP run/reference number. - Production order
or work order. - Parent item or finished product. - Component item. -
Requirement quantity. - Available stock. - Shortage quantity. - Required
delivery date. - Source planning run and generation date.

4.2 Manual PR

Capture: - Purchase justification. - Business requirement. - Requesting
department. - Requested item or service. - Estimated cost. - Supporting
documents. - Reason for manually initiating the requirement.

4.3 Repair PR

Support optional: - Equipment or machine ID. - Asset reference. -
Equipment location. - Breakdown or repair reference. - Breakdown date. -
Repair description. - Spare parts required. - Repair urgency. - Downtime
impact. - Maintenance/engineering reference. - Supporting photographs or
technical reports.

Equipment or machine ID is optional for Repair PR.

4.4 Maintenance PR

Support optional: - Equipment or machine ID. - Preventive or corrective
maintenance classification. - Maintenance schedule reference. -
Maintenance work order. - Planned maintenance date. - Required
spares/materials. - Service requirements, where applicable. -
Maintenance department. - Equipment criticality. - Technical
specifications.

Equipment or machine ID is optional for Maintenance PR.

Mandatory fields must be configurable by PR Type. Do not make equipment
ID mandatory for Repair or Maintenance PRs in Phase 1.

5.  PR Applicability and Menu Visibility

PR applicability must be configurable through existing General Settings.

Support: - Company. - Branch. - Group. - Business unit / plant, where
applicable. - Item category, where required. - PR Type. - Enabled /
disabled status. - Asset category exclusion. - Explicitly permitted
Asset exceptions.

Mandatory PR menu rule

The system must validate applicability before displaying the Purchase
Request menu.

1.  User logs in.
2.  Identify authenticated employee.
3.  Retrieve company, branch, department, group and business unit.
4.  Evaluate PR applicability using existing General Settings.
5.  If PR is enabled for the applicable branch and group, display the PR
    menu.
6.  If PR is disabled, hide the PR menu.
7.  If configuration is missing, invalid or ambiguous, deny PR access by
    default.
8.  Reevaluate after organizational assignment or configuration changes.

Apply the same centralized validation at the backend for module access,
PR creation, retrieval, editing, submission and approval.

Menu hiding alone is not sufficient security enforcement.

6.  Requester and Department Details

Automatically populate: - Requester name. - Employee ID. -
Designation. - Department. - Company. - Branch. - Group. - Business unit
/ plant. - Reporting Manager.

Capture: - Purchase purpose. - Business justification. - Cost centre. -
Delivery location. - Specifications. - Attachments. - Remarks.

Support authorized PR creation on behalf of another employee only if
permitted by existing RBAC.

Record actual creator and requesting employee separately.

7.  Unit-Specific Item Master

Different business units maintain their own Item Masters.

The PR must retrieve items from the selected and authorized business
unit’s Item Master.

Retrieve: - Item code. - Description. - Category. - UOM. -
Specifications. - Branch applicability. - Assigned buyer.

Prevent unauthorized cross-unit selection.

Do not create a duplicate Item Master.

8.  Buyer Configuration

Buyer assignment must be resolved through the existing Item Master based
on branch.

Required mapping: - Item code. - Item category. - Branch. - Assigned
buyer. - Active/inactive status. - Effective dates, where supported.

Support item-level buyer assignment when a PR contains multiple items.

If the same item has different buyers in different branches, resolve the
buyer using the applicable branch-specific mapping.

If buyer assignment is missing or inactive: - Do not automatically
assign another buyer. - Set the item/PR to Pending Buyer
Configuration. - Notify the authorized administrator. - Prevent the item
from being treated as ready for buyer action.

9.  PR Item Details and Approximate Pricing

Each PR supports multiple item lines.

Capture: - Item code. - Description. - Item category. - UOM. - Requested
quantity. - Approximate unit price. - Currency. - Estimated total
value. - Specifications. - Remarks.

Calculate:

Estimated item value = Requested quantity × Approximate unit price.

Calculate the PR estimated total from all item lines.

Approximate price is used for budgeting and approval routing. It is not
a final purchase price.

10. Multiple Delivery Dates and Quantities

Each PR item must support multiple delivery schedules.

Example:

  Item     Delivery date     Quantity
  -------- --------------- ----------
  Item A   15-Nov-2026            100
  Item A   30-Nov-2026            150
  Item A   15-Dec-2026            250
  Total                           500

Requirements: - Multiple delivery dates per item. - Independent quantity
for each schedule. - Total scheduled quantity must equal requested item
quantity. - Support editing schedules before submission. - Preserve
schedules after approval. - Maintain delivery schedule revision
history. - Apply reapproval when approved schedules change.

11. ERP Stock Availability Integration

Stock availability must be obtained through the existing ERP
integration.

Do not create fabricated stock balances or treat unavailable data as
zero stock.

Where the ERP interface supports it, retrieve: - Item code. -
Branch/plant. - Warehouse/store. - Stock on hand. - Reserved quantity. -
Blocked or unavailable stock. - Relevant committed quantity. - Available
quantity. - Retrieval timestamp. - ERP source reference.

Use the ERP’s authoritative availability calculation where provided.

If the ERP does not provide an authoritative available quantity,
document the calculation and source fields before implementing it.

Stock validation

-   Display stock availability during PR creation.
-   Identify potential shortages.
-   Show the source and retrieval timestamp.
-   Warn when ERP information is unavailable or stale.
-   Do not silently use cached or fabricated values as current
    availability.
-   Apply configured rules for stock checks when submitting the PR.

The stock check must not silently change the requested quantity.

Any inventory reservation or stock deduction is outside Phase 1 unless
an existing approved ERP workflow explicitly supports it.

12. Duplicate PR and Item Requirement Warning

The system must identify potential duplicate requirements.

Check relevant open PRs using: - Item code. - Company. - Branch. -
Business unit. - Requesting department. - Relevant open PR statuses. -
Applicable date range, where configured.

When a potential duplicate is found:

1.  Display a warning to the requester.
2.  Show relevant existing PR references according to RBAC.
3.  Display available quantities and statuses where authorized.
4.  Allow the requester to continue submitting the PR.
5.  Record that a duplicate warning was displayed.
6.  Record the user’s acknowledgement or justification where configured.

Duplicate detection is a warning, not a submission block.

Do not automatically reject or merge duplicate PRs.

13. Mandatory Budget Validation

Budget validation is mandatory before PR submission.

Reuse the existing budget and cost-centre functionality or the existing
authorized ERP integration.

Validate, where supported: - Company. - Branch. - Department. - Cost
centre. - Project/WBS, where applicable. - Financial year. - Budget
allocation. - Actual expenditure. - Existing commitments. - Available
budget. - Estimated PR value.

The budget validation must use the authoritative budget source
configured for the company.

Budget validation rules

1.  A PR must have the required budget assignment.
2.  Validate available budget before submission.
3.  Compare estimated PR value against available budget.
4.  If sufficient budget exists, allow submission to continue.
5.  If budget is insufficient, prevent submission under the mandatory
    validation rule.
6.  Record the budget validation result and timestamp.
7.  Show the requester the validation outcome.
8.  Preserve the budget source reference and relevant calculation
    details.
9.  Revalidate at submission to prevent reliance on stale draft-time
    checks.
10. Do not fabricate budget availability.

If budget integration is unavailable, the PR must not bypass mandatory
budget validation. Return a clear configuration/integration error and
notify the authorized administrator.

Budget reservation and actual budget consumption must follow existing
financial controls. Do not assume that merely submitting a PR reserves
or consumes budget.

14. Approval Workflow

Reuse the existing CIPPlatform Approval Workflow Engine.

Level 1 – Reporting Manager

Every submitted PR must first go to the requester’s Reporting Manager.

Level 1 approval is mandatory.

Resolve the Reporting Manager through the existing employee hierarchy.

Do not permit unauthorized self-approval.

Subsequent category and price-based approvals

After Level 1, evaluate: - Item category. - Estimated PR value. - PR
Type. - Applicable branch and group. - Configured approval level. -
Assigned approval manager.

Example configuration only:

  Category           Estimated value Approver
  -------------- ------------------- -----------
  Consumables          Up to ₹25,000 Manager A
  Consumables      ₹25,001–₹1,00,000 Manager B
  Consumables        Above ₹1,00,000 Manager C
  IT Equipment         Up to ₹50,000 Manager D
  IT Equipment         Above ₹50,000 Manager E

Administrators configure actual values and approvers.

Support PR Type-based workflow differences where explicitly configured.

Prevent overlapping or ambiguous approval rules.

Missing approval configuration must not silently bypass approval.

For multiple categories in one PR, evaluate all applicable approval
requirements and use existing sequential or parallel workflow
capabilities.

15. Approval Delegation, Escalation and SLA

Reuse existing workflow functionality where available.

Support: - Authorized approval delegation. - Approval escalation. -
Configurable approval SLA. - Pending approval reminders. - Rejection
comments. - Return-for-correction comments. - Complete approval
history. - Approval manager reassignment with audit.

Do not introduce a separate workflow engine.

16. Approved PR Changes and Reapproval

Approved PR changes may be initiated by all three authorized parties:

1.  Requester.
2.  Assigned buyer.
3.  Authorized administrator.

All three must follow the controlled change and reapproval process.

Change process

1.  User initiates a change request.
2.  System records the original approved values.
3.  System records proposed new values.
4.  User supplies a mandatory reason for the change.
5.  System identifies affected PR fields and items.
6.  System triggers the configured reapproval workflow.
7.  The PR is marked as Pending Reapproval.
8.  The original approved version remains available for audit.
9.  The revised version becomes effective only after all required
    reapprovals are completed.
10. The requester, buyer and relevant approvers are notified.

Fields subject to change control

-   PR Type.
-   Item code.
-   Item description where editable.
-   Item category.
-   Quantity.
-   Approximate unit price.
-   Estimated total.
-   Delivery dates.
-   Delivery quantities.
-   Cost centre.
-   Department.
-   Branch or business unit, where authorized.
-   Equipment reference.
-   Business justification.

Restrictions

-   Do not silently overwrite approved values.
-   Do not permit ordinary editing to bypass reapproval.
-   Do not erase earlier approval history.
-   Do not treat a proposed change as approved.
-   Do not permit unauthorized changes to organizational ownership.
-   PR Type changes must receive explicit authorization and reapproval.

Use the existing workflow engine to determine the required approval
levels for revised data.

A2. Bulk removal/archive of unapproved PR items after configurable XX
days

Add a configurable cleanup function for unapproved PR item/service lines
older than a business-defined number of days (XX).

Configuration: - Enable/disable cleanup. - Age threshold in days. Do not
hardcode XX; an authorized administrator must configure it. - Explicit
age calculation basis: line creation date, PR creation date, last
submission date or last activity date. - Eligible PR types, branches,
groups and statuses. - Exemptions for Urgent/Critical PRs, active
approvals, change requests, master-data review, budget checks, ERP
failures or other protected workflows. - Execution mode: preview only,
administrator-triggered bulk cleanup, or scheduled cleanup. - Advance
warning period and notification recipients.

Rules and safeguards: - Only unapproved lines matching configured
age/status rules are candidates. - Approved lines and approved
quantities must never be removed. - For partially approved lines,
preserve approved quantity and approval history. Only an eligible
unapproved balance may be archived if explicitly configured. - For
multi-line PRs, archive eligible lines individually; do not delete the
entire PR if other lines remain active or approved. - Do not clean up
records while a protected workflow is active unless explicitly permitted
by configuration. - Generate a preview showing PR number, line,
requester, branch, PR type, item/service, requested/approved/unapproved
quantity, status, age, eligibility reason and proposed action. - Require
authorized confirmation for manual bulk cleanup. Scheduled cleanup must
use approved configuration and produce a report. - Use soft
archive/removal, not physical deletion. Retain original data,
attachments/metadata references, approval history, user identity,
timestamps, cleanup reason, rule version, execution user/job and
execution time. - Recalculate parent PR status. If no active lines
remain, apply a configured expired/cancelled/closed status; do not
silently delete the PR header. - Notify requester, buyer and relevant
approvers according to configuration. - Produce skipped-record and
failure reports. - Prevent duplicate and concurrent cleanup execution. -
Allow authorized restoration where permitted. Restored lines must return
to an appropriate draft/returned state and must not silently regain
obsolete approvals. - Audit candidates, skipped records, removals,
failures and restorations.

Acceptance tests: 1. A line younger than XX days is not selected. 2. An
eligible line older than XX days appears in preview. 3. Approved lines
are never removed. 4. Partially approved lines retain approved
quantities and history. 5. Ineligible statuses and protected workflows
are skipped. 6. Multi-line PRs retain non-eligible lines. 7. Parent PR
status is recalculated. 8. Soft archive retains audit history. 9.
Scheduled and manual jobs enforce permissions. 10. Notifications and
exception reports are generated. 11. Concurrent jobs cannot process a
line twice. 12. Authorized restoration does not reinstate obsolete
approvals.
